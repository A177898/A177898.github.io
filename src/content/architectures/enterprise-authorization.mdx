## Architecture position


<PrincipleCallout>
  Enterprise authorization should be treated as a reusable decision capability that evaluates assigned authority, trusted context and policy without assuming ownership of every domain involved in the decision.
</PrincipleCallout>

Five key boundaries establish the architecture before component detail:

```text
Authentication
      ≠
Authorization

Entitlement Assignment
      ≠
Authorization Evaluation

Policy Decision
      ≠
Policy Enforcement

Authorization Context
      ≠
Domain Ownership

Authorization
      ≠
Domain Invariants
```

Governing principle:

<PrincipleCallout>
  Centralise what needs to be consistent. Federate what needs to remain authoritative within its domain.
</PrincipleCallout>

## Purpose

This reference architecture defines a **logical** model for enterprise authorization as a reusable decision capability.

It separates:

- proving identity from determining authority;
- assigned authority from effective authority;
- policy decision from policy enforcement;
- decision-relevant context from domain ownership;
- authority to attempt an action from domain validity of that action.

The architecture is vendor-neutral and product-agnostic. It does not prescribe a specific policy language, identity provider, entitlement store or runtime technology.

## Problem

Enterprise authorization frequently begins with a simple permission model and expands under business pressure into role proliferation, inconsistent application-embedded rules, unclear ownership of decision attributes, and fragile synchronous dependency chains.

Without explicit boundaries, authorization becomes either:

- too centralised — extracting domain authority into a bottleneck; or
- too fragmented — embedding the same business rule differently across applications, APIs and interfaces.

## Objectives

- Establish authorization as a **decision capability**, not only a permission lookup.
- Keep domain information **domain-owned**.
- Separate **assignment**, **evaluation** and **enforcement**.
- Support **contextual** decisions with explainable outcomes and obligations.
- Enable policy evolution independent of application release cycles where appropriate.
- Fail securely when sufficient authority cannot be established.
- Provide a deployment-agnostic logical model from which implementation patterns can be derived.

## Core decision contract

The decision contract is a formal architecture interface — not an OpenAPI specification.

### Hybrid authorization model

This reference adopts a **hybrid** authorization model. The mechanisms below are complementary, not interchangeable substitutes:

- **Roles** represent broad assigned responsibility (what class of authority a subject holds).
- **Attributes** constrain when that authority applies (conditions on subject, resource or environment).
- **Relationships** establish relevant subject/resource association or delegated scope (who relates to what, and with what mandate).
- **Contextual policy** evaluates the combination of assigned authority, attributes, relationships and request context for a specific action.

Together they support decisions of the form Subject + Action + Resource + Context, without prescribing a particular policy engine, policy language or storage schema.

```text
AUTHORIZATION REQUEST

Subject
Action
Resource
Context

        ↓

AUTHORIZATION EVALUATION

Applicable Authority
Trusted Context
Applicable Policy

        ↓

AUTHORIZATION RESPONSE

Decision
Reason
Obligations
Decision Reference
Policy Reference
Validity Context
```

Conceptual expression:

```text
authorize(
    subject,
    action,
    resource,
    context
)
→
decision,
reason,
obligations,
decisionReference
```

### Decision semantics

```text
Decision:
ALLOW | DENY
```

Conceptual reasons:

```text
INSUFFICIENT_AUTHORITY
RESOURCE_OUT_OF_SCOPE
LIMIT_EXCEEDED
MANDATE_NOT_SATISFIED
SOD_VIOLATION
CONTEXT_INSUFFICIENT
```

Conceptual obligations:

```text
STEP_UP
REQUIRE_APPROVAL
REQUIRE_SECOND_AUTHORIZER
```

```text
Decision ≠ Reason ≠ Obligation
```

Blocking-obligation semantics are shown in the [runtime decision flow](#runtime-architecture). ALLOW with an unmet blocking obligation does **not** permit execution.

## Logical reference architecture


This is the primary logical model. It communicates **responsibility**, not physical topology.

Authorization Context is not a database and not necessarily a service. PDP is not necessarily one central physical service. Domain Authorization is not automatically central policy. Domain Invariants remain domain-owned. PEP, PDP, PIP and PAP are architectural responsibilities.

## Attribute acquisition patterns


### A — Authoritative lookup

```text
PDP → Authoritative Domain
```

Freshness advantage; runtime dependency and latency trade-off.

### B — Trusted request context

```text
Trusted Caller
      ↓
Authorization Request
      ↓
PDP
```

Low retrieval overhead; provenance and trust are critical.

### C — Decision projection

```text
Authoritative Domain
      ↓
Domain Change
      ↓
Decision Projection
      ↓
PDP
```

Performance and resilience advantage; freshness and consistency trade-off.

### D — Hybrid

```text
Trusted Request Context
          +
Decision Projection
          +
Selective Authoritative Lookup
          ↓
Authorization Context
```

No single pattern is universally preferred.

## Attribute provenance


```text
Attribute
   ├── Value
   ├── Provenance
   ├── Authoritative Source
   ├── Freshness
   └── Integrity Evidence
              ↓
       Trust Determination
```

```text
Caller-supplied claim
        ≠
Trusted authorization attribute
```

## Attribute classification and correctness


| Characteristic | Question |
|---|---|
| Authority | Which domain owns it? |
| Provenance | Can its source be established? |
| Trust | Can the source be trusted for this decision? |
| Freshness | How current must it be? |
| Volatility | How frequently does it change? |
| Sensitivity | What security/privacy constraints apply? |
| Latency | How quickly must it be available? |
| Availability | What happens when its source is unavailable? |
| Correctness | What is the consequence of stale information? |

These correctness classes are **conceptual categories**, not mandatory industry standards. Classification guides selection among trusted request context, authoritative lookup, projection and caching. No acquisition mechanism automatically guarantees correctness.

Authorization information has a **correctness window**, not merely a technical cache TTL. An operationally healthy cache may still contain information that is too stale for the protected decision. Freshness requirements depend on the consequence of stale information.

Trust derives from source authority, provenance and integrity controls; callers cannot simply assert trust. The provenance model above is conceptual, not a prescribed payload schema.

### Class A — Request-bound

Information must represent the exact protected request.

Examples: transaction amount, target resource, requested action.

### Class B — Immediate or near-immediate revocation

Changes require a tightly bounded correctness window.

Examples: suspended authority, revoked relationship, emergency access removal.

### Class C — Bounded stale

Some propagation delay may be acceptable, with the acceptable window explicitly defined by the implementation context.

### Class D — Versioned reference

Information changes through controlled publication.

Examples: policy definitions, permission taxonomy, reference configuration.

```text
Technical Cache Validity
          ≠
Authorization Correctness
```

## Policy lifecycle


Control plane and runtime plane are distinct. The runtime should not require the policy-authoring interface to be available for every decision.

```text
CONTROL PLANE

Policy Author
     ↓
Policy Administration
     ↓
Validation
     ↓
Simulation / Testing
     ↓
Review
     ↓
Approval
     ↓
Publication
     ↓
Published Policy

────────────────────────

RUNTIME PLANE

Published Policy
     ↓
PDP
     ↓
Runtime Decisions
```

### Policy versioning

Published policy should be **identifiable by version** so that:

- runtime evaluation uses a known published version;
- decisions and decision evidence can be associated with the version actually evaluated;
- distribution and activation of new versions are controlled;
- distributed evaluators can reason about propagation and consistency windows;
- rollback targets an approved prior version under governance.

This reference does not prescribe version-number syntax, rollout technology or universal propagation deadlines. Those belong to the implementation context.

## Decision validity


Authorization decisions may be:

- request-scoped;
- operation-scoped;
- valid for a bounded period;
- invalidated by material context change.

This reference does **not** invent a default TTL.

Architecture question:

> What is the validity scope and lifetime of this authorization decision?

```text
NEW AUTHORIZATION REQUEST

Cannot establish authority
        ↓
Do not grant
```

```text
EXISTING AUTHORISED PROCESS

Authorization dependency changes
        ↓
Evaluate:
Decision validity
Revocation semantics
Workflow state
Risk
Protected action
```

## Resilience


Failure modes include:

```text
PDP unavailable
Published policy unavailable
Entitlement context unavailable
Authorization context unavailable
Authoritative source unavailable
Projection stale
Partial context
Audit unavailable
Policy propagation failure
```

> If sufficient authority cannot be established, authority should not be granted.

> Fail closed is a security posture, not a complete resilience strategy.

Possible implementation considerations (options, not mandates):

- replicated decision capability;
- replicated published policy;
- local decision information;
- bounded caching;
- decision projections;
- timeout budgets;
- circuit breaking;
- regional evaluation;
- controlled degradation.

## Deployment patterns


Four implementation-neutral patterns. None is ranked as universally preferred.

### Central decision service

```text
Consumers → Central PDP
```

Strengths: consistent evaluation, central governance. Trade-offs: latency, availability concentration, blast radius.

### Distributed decision nodes

```text
Policy Distribution
        │
  ┌─────┼─────┐
  ▼     ▼     ▼
PDP A PDP B PDP C
```

Strengths: locality, scale, failure isolation. Trade-offs: policy propagation, consistency windows, operational complexity.

### Embedded evaluation

```text
Application
    └── Local Policy Evaluator
```

Strengths: low latency, local autonomy. Trade-offs: policy distribution, drift risk, governance overhead.

### Hybrid

Different authorization classes may use different deployment patterns.

### Deployment decision flow

```text
Authorization Requirements
          ↓
Latency / Availability / Scale
          ↓
Data Residency / Failure Domains
          ↓
Policy Consistency
          ↓
Attribute Correctness / Freshness
          ↓
Operational Model
          ↓
Deployment Pattern
          ↓
Technology Selection
```

Technology selection comes **after** architecture requirements.

### Platform criticality

```text
More Consumers
      ↓
Greater Reuse
      ↓
Greater Enterprise Leverage
      ↓
Greater Criticality
      ↓
Greater Blast Radius
```

Increased adoption typically increases expectations around availability, capacity, disaster recovery, regional architecture, change governance, compatibility, policy rollout, rollback, observability and incident response.

## Audit and explainability


```text
Authorization Decision
       │
       ├───────────► Runtime Response
       │
       └───────────► Decision Evidence
                           │
                           ▼
                    Audit / Observability
```

Potential evidence:

- subject reference;
- action;
- resource reference;
- decision;
- reason;
- obligations;
- policy ID/version;
- relevant decision context;
- correlation identifier;
- timestamp.

Avoid:

- raw tokens;
- secrets;
- complete sensitive payloads;
- unnecessary PII.

```text
Internal Decision Evidence
          ≠
External Error Response
```

### Observability

Operational observability is distinct from decision audit evidence.

Useful operational categories include:

- decision latency and errors;
- dependency availability (PDP, published policy, context sources);
- stale or missing context signals;
- policy-version distribution health;
- obligation coordination and re-evaluation failures;
- correlation across evaluation and enforcement.

Numerical latency or availability targets remain implementation-specific. Observability must respect the same data-minimisation expectations as audit evidence.

### Security considerations

This architecture’s security position synthesises existing principles rather than introducing a separate control catalogue:

- **Deny by default** ([AP-02](#ap-02)) — authority must be positively established.
- **Authoritative enforcement** — PEP placement must protect the real action; UI-only checks are insufficient ([Enforcement placement](#enforcement-placement)).
- **Trusted subject and context** — provenance and integrity controls; callers cannot simply assert trust ([Attribute provenance](#attribute-provenance), [AP-08](#ap-08)).
- **Request and resource binding with decision validity** — decisions apply to a defined request/validity scope ([Decision validity](#decision-validity)).
- **Secure handling of obligations and failures** — unmet blocking obligations and evaluation failures must not broaden authority ([Runtime architecture](#runtime-architecture), [Resilience](#resilience)).
- **Protected policy administration** — control-plane publication is governed and distinct from runtime evaluation ([Policy lifecycle](#policy-lifecycle)).
- **Minimised audit data and limited external error detail** — evidence retention without unnecessary secrets or PII ([Audit and explainability](#audit-and-explainability)).

This synthesis does not invent employer-specific controls, protocols, token formats or mandatory infrastructure.

## Quality attributes

Quality attributes for this architecture include:

- Performance
- Availability
- Scalability
- Consistency
- Freshness
- Correctness
- Resilience
- Security
- Auditability
- Explainability
- Operability
- Compatibility

Measurable targets belong to the **implementation context**. This reference does not invent numerical thresholds.

## Architecture trade-offs

These tensions have no single correct answer:

### Centralisation vs autonomy

Consistency versus dependency and bottleneck risk.

### Freshness vs availability

Authoritative retrieval versus local decision resilience.

### Consistency vs latency

Central evaluation versus distributed evaluation.

### Rich policy vs explainability

Expressiveness versus understandable, testable and governable policy.

### Context richness vs privacy

Decision quality versus sensitive-data processing.

### Reuse vs blast radius

Enterprise leverage versus consequence of failure.

### Enterprise consistency vs domain authority

Common semantics versus keeping decisions with the domain best placed to make them.
